01 — What you get

Six checks. One verdict.

Every audit runs the same six tools against your code. Each one returns evidence — an error, a line number, an axiom trace — not a score.

lean_checkpass / fail

Does it actually compile? Your code is built against Lean 4 and Mathlib. You get a pass/fail verdict with the exact error message and line for anything that fails — no paraphrase.

lean_axiomsaxiom dependency audit

What is the proof standing on? Every axiom your theorems transitively depend on is listed. This is the check that catches a hidden sorryAx — a sorry buried three lemmas deep still makes the headline theorem unproven, and this tool surfaces it.

lean_proof_dependencemutation-tested

Does the proof actually use the hypotheses your statement advertises? Each hypothesis is deleted from the statement — proof untouched — and Lean is asked to re-check it. If it still compiles, the proof never depended on that hypothesis. Reported as measured dependence, with the mutated statement attached, never as a guess.

lean_audit_corpusstatement-level · adversarial

Do the statements hold up under attack? For a corpus or library, each statement gets adversarial checks at the statement level — vacuous hypotheses, trivially-true formulations, and claims weaker than their names suggest. A kernel pass alone does not catch these.

lean_explain_failurefailure diagnosis

Why did it break, in the smallest possible piece? A failing file is reduced to the minimal failing fragment, and the failure is classified — missing import, type mismatch, unprovable goal, tactic failure — so you know what kind of fix you’re looking at before you start.

lean_verify_claimclaim ↔ formalization

Does the formalization match the claim? The theorem you proved is compared against the claim you say you proved. Mismatches — a dropped hypothesis, a weaker conclusion, a quantifier in the wrong place — are flagged for review. The most expensive Lean bug is a correct proof of the wrong statement.

04 — Why it matters

A kernel pass is not an audit.

6

Tools in every audit. Check, axioms, proof dependence, corpus, failure diagnosis, and claim verification — the same pipeline, run the same way, every time.

Lean’s kernel is exact: if it accepts a proof term, the proof is valid for the statement as written. That guarantee is real — and narrower than most people assume. It says nothing about a sorry hiding in a dependency, nothing about a hypothesis that makes the theorem vacuous, and nothing about whether the statement on the page is the claim in your paper.

That gap is where this audit lives. It was built by a Lean 4 practitioner who ran it against his own 921-theorem corpus first — and whose own adversarial pass found 22 issues in code that already passed the kernel. Your code gets the same treatment his got.
